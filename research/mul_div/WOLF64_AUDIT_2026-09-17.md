# Wolf64 MUL_DIV audit — 2026-09-17

Source snapshot:

```text
Kweepa/Wolf64 @ d606a14bbfb9fb17059c24824e0d921f23fd6860
```

This audit asks the same question as the Quake64/Steel Ranger pass:

> Does a real game contain a dynamic `(a*b)/d` workload where a reusable library routine is genuinely preferable to the game's existing LUT/constant/bounded specialization?

## 1. Sprite/item horizontal projection

`src/items_draw.asm` computes:

```text
e_col_cx = 20 ± min(30, |side| * 20 / perp_mid)
```

The numerator and denominator are dynamic, so this superficially resembles a perfect `MUL_DIV` call.

However, the game has several important special properties:

```text
multiplier = 20          ; compile-time constant
result is clamped <= 30
division helper saturates <= 40
input widths are inspected and specialized
```

The existing `div_q40` has separate paths for:

- 8/8;
- 16/8;
- 16/16;

and stops once the quotient reaches 40. For small 8/8 quotients it uses repeated subtraction, which is exactly the kind of bounded-output specialization a general-purpose library should not pretend is unavailable.

### Decision

```text
General 16x16/16 MUL_DIV: REJECT for this call site.
```

The operation is dynamic, but the constant multiplier and tiny bounded quotient make a game-specific exact implementation easy to fake efficiently.

A library replacement would need to exploit the same semantic constraints, for example a dedicated projection/ratio helper, not charge for full-width generality.

---

## 2. Wall-height projection

Wolf64's table generator precomputes wall-height behavior for the common depth range. The generated table is approximately:

```text
half_h ~= constant / depth_index
```

with a special exact-divide path only for the near/exception region.

This is another direct validation of the roadmap law:

```text
fixed/static mapping -> LUT first
```

A generic runtime MUL_DIV would be the wrong optimization target here.

### Decision

```text
General MUL_DIV for ordinary wall height: REJECT.
LUT + exceptional exact path: appropriate game architecture.
```

---

## 3. Texture/sprite horizontal scaling

The item renderer does not repeatedly divide for every output column. It initializes a numerator/denominator state, then advances it incrementally in the column loop:

```text
accumulator += source_width*2
while accumulator >= screen_width*2:
    accumulator -= screen_width*2
    source_column++
```

This is effectively a Bresenham/DDA-style prepared ratio.

That is very important for our design work. It is a real production example of the pattern we identified in Quake64:

```text
prepare ratio once
apply/increment cheaply many times
```

The game correctly avoids a general `(a*b)/d` call per column.

### Decision

```text
Repeated same-ratio work: STRONG evidence for PREPARED RATIO / DDA,
not for repeated generic MUL_DIV.
```

---

## 4. Enemy AI division

`src/enemy_ai.asm` contains a dynamic:

```text
(dt8 << 2) / ai_dist
```

implemented as a short bit-divider.

This is dynamic but has:

- a fixed power-of-two numerator scale;
- small widths;
- no general multiplication.

It is therefore a division/fixed-point helper question rather than evidence for `MUL_DIV`.

### Decision

```text
Not a MUL_DIV justification.
```

---

# Overall Wolf64 result

Wolf64 gives us essentially the opposite result from a synthetic arithmetic benchmark.

It repeatedly demonstrates that high-performance C64 game code wins by exploiting:

- constant multipliers;
- tiny bounded quotients;
- precomputed tables;
- exceptional slow paths;
- prepared/incremental ratio state.

That means the current ~816-cycle general bounded `UMULDIV16` still does **not** earn a stable API slot from Wolf64.

But Wolf64 strongly supports the next direction:

```text
PREP_RATIO / APPLY_RATIO
or
DDA-style prepared scaling state
```

especially when the same denominator/ratio is reused many times.

Combined with Quake64 near clipping, the real-game evidence now points consistently toward:

```text
single arbitrary exact ratio:
    keep general MUL_DIV as fallback/internal research

reused dynamic ratio:
    prepared ratio / reciprocal

tiny geometry-specific ratio:
    absorb into the compound geometry routine

fixed/static ratio:
    LUT / precompute / shifts
```

That is a much stronger fit to the implementation-plan laws than promoting one universal full-width routine.

# UMUL32: five historical source-linked variants on identical public frame inputs

This comparison builds each of the **five already certified UMUL32 sources**
through the operation-first installer, pins the exact candidate, and executes
150 calls spread over 24 synthetic frames. The caller X/Y/Z public bytes,
A/X/Y/C/D initial state, operand values, and code/I/O placement are **identical
for every candidate**. Every call checks the full 64-bit mathematical result,
X/Y input preservation, C=0 and stack balance. Source-generated bytes match
the actual linked PRG, and code changes are limited to the FAST31's certified
self-modifying operand sites.

Qualifying scripts:

```sh
python3 -m unittest discover -s tools -p 'test_umul32_all_five_paired_frames.py' -v
python3 tools/umul32_all_five_paired_frames.py --out build/umul32_five_frame_report.json
```

Two independent placements are evaluated: `$8000/$C000` and
`$7123/$C040`. For each, the report records:

- Actual linked source and PRG SHA-256, RAM and ZP resource use.
- Same-input mean public call cycles for all five Pareto choices.
- Total 24-frame math cycles, **peak** and p95 frame math cycles.
- Count and maximum size of **individual slower calls** and regressed
  frames versus the compact zero-ZP baseline.

The comparison reuses the previously authenticated UMUL32 192-input
edge/random source corpus; its 150-call frame sequence is deterministic.
Each frame's score includes caller JSR cost as a fixed six-cycle term in
`tools/frame_cycle_budget.py`. The code introduces no new arithmetic
routines and makes **no claim that the historical fastest kernel wins every
call or that model cycles include PAL VIC/IRQ, SID or REU contention**.

The five sources have materially different resource contracts. The
FAST31 source family needs 31 private ZP bytes, writable code and 2,560
bytes of code/tables, while the compact source uses 0 ZP and only 204
bytes of code plus 12 ordinary scratch bytes. A higher-speed candidate
that exceeds a project's memory/ZP or writable RAM budget must not be
selected. Keep V1–V5 reference builds until source, hardware, and
busiest-frame parity across all relevant workloads is established.

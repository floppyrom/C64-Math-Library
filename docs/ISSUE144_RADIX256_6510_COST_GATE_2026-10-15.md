# Issue #144 B — radix-256 6510 REU digit feasibility / no-go checkpoint

**15 October 2026. Research-only, V4. No public resident/REU or OptiSearch publication.**

## Mathematical proof

The source-independent 1,155,360-pair oracle passes full N32/D16 for three bounded radix-256 quotient estimators (high-byte divide, reciprocal, and a single-REU-bank direct q0/t0 table). Lookup uses 128×256×2 = 65,536 bytes; v=Dnorm>>8, h=Rnorm>>8, lookup offset = ((v-128)<<9)|(h<<1). Each estimate needs no more than two table corrections. Dedicated numerical CI: [#38728754571](https://github.com/floppyrom/C64-Math-Library/actions/runs/38728754571).

## Actual executable NMOS 6510 screen

The self-contained 199-byte **one quotient digit** at $0D00 uses:
- V4's otherwise unallocated REU bank $20 for the 64-KiB table;
- scratch $70–$7F (**16 additional ZP bytes**, not part of current reserved normal ZP pools);
- direct REU DMA of two bytes to $76/$77;
- eight-round software shift/add 8×8 product q0×Dlow (no native UMUL8 call); and
- exact signed 24-bit remainder with bounded ±2 corrections.

File: `tools/issue144_u3216_reu_digit_6510_screen.py`. 4,040 same-input digit cases, including boundary denominators, all pass Qdigit/R16/C/SP/input preservation on the assembled 6510 emulator backed by the published V4 REU resident image. Mean **446.705 modeled CPU cycles per digit**, p95 **516**, max **569**, excluding actual REU bus wait. Dedicated [CI #38730137724](https://github.com/floppyrom/C64-Math-Library/actions/runs/38730137724) **PASS**.

### Important REU resource conflict

An earlier experiment attempted to call normal `MATH_UMUL8` immediately after a REU lookup; it **failed** at R=$0100,D=$8001,next=$00, returning q=2,R=0 instead of q=1,R=$7FFF. The existing V4 REU-assisted UMUL8 shares $DF02–$DF0A controller state with the trial lookup and cannot be chained without restoring the REU configuration and preserving lookup bytes. Failures: [CI #38729816892](https://github.com/floppyrom/C64-Math-Library/actions/runs/38729816892). Never describe this combination as integrated or production-safe. Replacing the multiply with self-contained 8-round code made the digit correct, but not fast.

## Matched two-digit lower-word cost gate

To isolate the actual architecture cost, `tools/issue144_u3216_radix256_optimistic_cost_gate.py` compares **698 identical N32/D16 operand pairs** with D≥$8000, where normalization shift s=0, so every input is unrestricted full width. Each method consumes two lower quotient bytes after the *same oracle-seeded high-word remainder* and validates the exact low quotient and full remainder against integer division.

| Case | Mean cycles, two digits | p95 | Note |
|---|---:|---:|---|
| Validated shared-subtract 16-step restoring tail | **460.599** | 521 | Executable placed model, no REU |
| Real REU q0/t0 + software 8×8 multiply | **893.676** | 983 | Executable 6510 model, **all 698 slower** |
| REU q0/t0, *free oracle product* | **351.722** | 408 | **Not executable:** multiplication injected at zero cost |
| *Free oracle table and product* | **231.722** | 288 | **Not executable:** both injected at zero cost |

Dedicated [CI #38730630823](https://github.com/floppyrom/C64-Math-Library/actions/runs/38730630823): **PASS**. The real producer costs **433.077 extra CPU cycles** over the existing lower-word restoring tail on this corpus, even before divisor normalization and any actual REU DMA/VIC bus overhead. These comparisons are tail-only and do not measure the complete public call; all code variants share the same mathematical oracle high-word seed.

A useful **optimistic multiplication speed threshold** follows from the oracle-product row: even with an impossible zero-cost call setup and no REU state restoration, each of two 8×8 multiplications must average **less than (460.599−351.722)/2 = 54.438 modeled cycles** merely to tie this tail, and **less than 42.923 cycles** to beat it by 5%. The shipped V4 `MATH_UMUL8` averages **69 cycles per public call** (excluding DMA wait), already slower than the tie threshold; calling it also requires restoring the clobbered REU controller and preserving scratch. The complete division has additional high-word, normalization and public ABI costs.

## Decision / next work

**Reject promotion of this straightforward radix-256+REU+8×8 approach as a general all-domain UDIV32_16/UMOD32_16 producer.** Its numerical exactness is established but hardware cost is not competitive on full-width inputs. A fundamentally cheaper quotient-digit multiply, a shared/delayed REU state, or an entirely new producer (not a guard) would be needed. Keep the 64-KiB q0/t0 table and correction proof as reproducible negative R&D results. Do not check off Issue #144 B.

These results do **not** refute all possible radix-256 dividers: the lower-bound 231.7-cycle result indicates theoretical headroom with a radically different lookup/product implementation. They refute the presently assembled REU-lookup + shift/add datapath as a default C64 replacement.

`PERFORMANCE.md`, five resident PRGs, two REU images, normal API, default ZP and public source generator remain unchanged. This branch intentionally is not package-sealed or merged into main. All experiments are independent of private OptiSearch source.
